# PlayEdu 后端实习一周学习计划

## 时间与目标

周期：7 天，每天约 3～4 小时，总计约 21～28 小时。默认你已有 Java、SQL 和 Spring Boot 基础；初次镜像下载与构建可能额外占用时间。

一周目标：跑通项目，讲清登录与课程查询，深入理解学习心跳和积分兑换，完成一项小范围个人实践，整理真实的简历描述。重点掌握两条核心业务链，其他模块先了解职责。暂不系统学习 React、LDAP、文件分片上传，也不要求完整性能压测。

当前项目是 Java 17、Spring Boot 3、MyBatis-Plus、MySQL、Redis、Redisson 的 Maven 多模块应用。多模块与双实例部署都不等于微服务。

每天分配：约 30 分钟补必要概念，90 分钟跟代码，60～90 分钟实验，20 分钟总结。环境或基础不足时优先完成主线，把额外内容留到后续，不把未验证的内容写成已掌握。

## 七天任务总览

| 天数 | 重点 | 必须完成的动手任务 | 当天产出 |
| --- | --- | --- | --- |
| 第 1 天 | 启动项目与业务全貌 | 启动本地栈，登录管理端，准备测试学员、课程、课时和播放资源；用学员账号走通课程访问 | 启动记录、一张架构图、测试数据说明 |
| 第 2 天 | 课程查询与登录鉴权 | 跟完一个课程详情接口；跟一次登录；验证无 Token 与无权限请求 | 查询与登录两条调用链、核心表关系图 |
| 第 3 天 | 学习心跳与活跃租约 | 跟踪首次心跳、续期和停止；用两个标签页或接口客户端竞争不同课时；验证旧会话和租约过期 | 会话状态图、请求与响应证据 |
| 第 4 天 | 学习事务、首次奖励与排行榜 | 查看有效心跳引起的数据库变化；完成课程后重试，核对奖励；定位提交后更新排行榜和重建入口 | 事务边界图、奖励幂等说明、MySQL 与 Redis 的职责说明 |
| 第 5 天 | 积分兑换、幂等与并发 | 正常兑换；同请求键重试；两个用户竞争最后一枚码；验证余额不足或售罄 | 兑换时序图、余额/流水/库存/兑换记录核对表 |
| 第 6 天 | 个人实践与验证 | 在已有覆盖之外补一个有效测试，或修复一个能复现的小缺陷；运行相关测试与后端检查 | 任务说明、代码差异、测试证据 |

## 第 1 天：先能运行、能操作、能介绍

阅读 [README](../README.md)、[后端文件职责指南](backend-file-guide.md) 的模块汇总、根目录 compose.yml 和后端父 pom.xml。

从仓库根目录运行：

```powershell
docker compose up -d --build
docker compose ps
```

走通“管理员配置课程 → 学员登录 → 查看并播放课程”。课程播放所需存储与资源配置以实际环境为准。构建失败就先定位日志，不跳过运行环节。

架构图标出三个客户端、API、MySQL、Redis 和对象存储。说明六个后端模块：api 管接口与编排，common 管基础业务与公共能力，course 管学习，points 管积分，resource 管资源，system 管初始化与横切处理。

**验收：**能用自己的话解释项目用户、业务流程和部署组成。

## 第 2 天：学会从请求跟到 SQL

代码入口：学员端 CourseController → CourseService/实现 → Mapper/SQL → 数据表；LoginController → LoginBus → 认证服务；FrontInterceptor、FCtx、ExceptionController。

先跟课程详情，再跟登录。记录实际参数、身份来源、权限检查、查表方式和响应。查看课程、章节、课时及学员相关表结构。用接口工具验证无 Token、无权限和非法参数，定位对应处理位置。

补知识：依赖注入、参数校验、JWT/Token、认证与授权、ThreadLocal 请求结束清理。

**验收：**脱离源码讲清课程查询与登录，不只说“Controller 调 Service”。

## 第 3 天：弄懂学习心跳

入口：[HourController.ping](../playedu-api/playedu-api/src/main/java/xyz/playedu/api/controller/frontend/HourController.java)、ActiveLearningLeaseService 及相关测试。

依次实验：首次创建会话、携带 session_id 续期、竞争不同课时、停止当前会话、使用旧 session_id、等待租约过期后重新学习。把预期与实际结果写成场景表。

回答：为什么不直接相信前端时长？session_id 和 TTL 各解决什么问题？多 API 实例为什么要共享租约状态？单活跃学习会话解决并行会话协调，不能描述成完整防作弊方案。

**验收：**能画出创建、续期、冲突、失效、停止的状态变化，指出当前代码如何计算有效时长。

## 第 4 天：区分事务事实与排行榜

入口：LearningFactPersistenceService、CourseCompletionTransition、DailyLearningRankingService、排行榜事件监听器；按需查 [文件指南](backend-file-guide.md)。阅读 ADR [0002](adr/0002-project-daily-learning-ranking-to-redis.md)、[0016](adr/0016-commit-course-rewards-with-learning-facts.md) 和 [0022](adr/0022-use-credit1-as-the-current-points-balance.md)。

跟踪一次有效心跳引起的课时、课程进度、时长明细和统计变化。测试首次课程完成及重试，查看积分余额和奖励流水，找出防重复机制。

画图标出：学习事实和奖励在同一 MySQL 事务中；排行榜在事务提交后更新，可从 MySQL 重建。定位 RedisDistributedLock 的一个真实调用，区分 Redis 锁和 MySQL 行锁。

**验收：**能说明事务回滚范围、重复奖励如何避免、排行榜失败的影响，以及 Redis 与 MySQL 之间不属于同一事务的状态边界。

## 第 5 天：深入积分兑换

入口：[PointRedemptionServiceImpl.redeem](../playedu-api/playedu-points/src/main/java/xyz/playedu/points/service/impl/PointRedemptionServiceImpl.java)、PointBalanceServiceImpl、相关 Mapper；参考 [积分首发清单](points-launch-checklist.md) 准备数据与对账。

按实际代码顺序列出：资格和商品校验、重复请求处理、数据库加锁、库存码选择、扣分与流水、发码、兑换记录。查看 requestKey、唯一约束及 FOR UPDATE 的作用。

必须验证四类场景：正常兑换、相同请求键重试、不同用户竞争最后一枚码、余额不足或售罄。核对最终余额、流水、库存和兑换记录。并发证据应来自确实重叠的请求或已有并发测试；连续点击两次只能证明重复请求行为。

**验收：**能区分请求重试和并发竞争，说明事务、幂等键、唯一约束、行锁的职责。能解释扣分后失败为何回滚。

## 第 6 天：形成一项个人贡献

只选一个任务，限定在当天可独立完成：

1. 有复现证据的小缺陷：补回归测试并修复，证明修复前失败、修复后通过。
2. 未发现缺陷：阅读已有测试，补一个没有覆盖的有价值场景，例如跨商品重复请求键的实际约定、兑换中途异常后的数据回滚、旧学习会话不能停止新会话。先确认现有约定和覆盖情况，再决定任务。

测试要检查业务结果和数据库状态，不能仅重复实现逻辑。如果测试发现的问题超出一天能安全解决的范围，保留复现与分析，如实记录未修复状态，不宣称完成。

在 playedu-api 父工程目录运行：

```powershell
.\mvnw.cmd test
.\mvnw.cmd spotless:check package
```

集成测试条件从现有测试读取；记录跳过项，构建成功不能替代并发验证。交付说明只写四点：具体问题、个人修改、验证证据、剩余限制。

**验收：**有可审阅的代码差异和实际运行结果；能解释为什么这项测试或修复有价值。

## 第 7 天：把实践变成可追问的项目经历

整理架构图、两条核心业务时序图、实验记录与个人贡献。练习 3 分钟介绍：30 秒业务与技术栈，60 秒学习链路，60 秒积分兑换，30 秒个人工作与结果。

建议项目名称：**基于 PlayEdu 的企业培训平台二次开发（个人项目）**。

简历按“项目能力”和“个人职责”区分事实。项目能力可以介绍现有学习进度、积分兑换等模块；个人职责只写实际完成的开发、修复或验证。

完成对应实践后可使用的职责示例：

> 补充积分兑换异常回滚测试，验证发码失败时用户余额、积分流水、库存状态和兑换记录保持一致。

若只是阅读或运行现有代码，就如实描述学习与验证，不写“独立设计实现”。性能数字只使用自己的测量结果，保留环境与测试条件。一周内没有完整压测结果就不写并发规模或性能提升百分比。

## 面试自测：十题必须能结合项目回答

1. 项目解决什么问题？你实际做了哪部分？
2. 为什么这是 Maven 多模块应用，而不是微服务？
3. 请求如何获取当前用户并检查权限？ThreadLocal 为什么清理？
4. 学习时长如何计算，为什么不接受任意前端上报值？
5. 两个标签页、两个 API 实例同时学习时，租约如何工作？
6. 学习事实和首次完成奖励的事务边界在哪里？
7. 排行榜更新失败或 Redis 数据丢失后如何恢复？
8. 兑换重复提交与最后一枚码竞争分别如何处理？
9. FOR UPDATE 锁什么？扣分后异常会怎样？
10. 你的改动如何证明有效？还存在哪些未验证内容？

答不出的题回到对应代码与实验，优先补主线，不用背脱离项目的答案。

## 可选加练与最终交付

提前完成当天任务时，任选一项：阅读共享限流和登录失败计数；理解兑换码加密与去重；按 [双实例验收文档](acceptance/multi-instance-learning.md) 跑 start/status/probe/stop。完整负载测试和查询优化留到后续。

最终至少保存：

- [ ] 架构图、核心表关系、学习心跳和积分兑换流程图。
- [ ] 登录与核心业务的请求、响应及数据库验证记录。
- [ ] 一项个人实践的代码差异、任务说明和测试结果。
- [ ] 简历草稿、3 分钟讲解稿、十题自测及未验证项。

每天笔记只写：今天解决的问题、代码入口、实验步骤、预期与实际、证据、未懂的问题。所有数据修改与故障实验仅在本地测试环境执行，笔记不保存密码、Token、密钥和兑换码原码。

若每天只有 2 小时：优先完成启动、查询与登录、两条核心业务阅读和最小实验，取消可选加练；第 6 天选择一个最小的测试贡献。此时应把成果定位为项目入门与初步实践，个人职责以实际完成的工作为准。
